The problem is that "autonomous" today means one of two things in practice: either the agent asks for permission constantly and becomes useless, or it runs completely unchecked and eventually does something it shouldn't have. veither is acceptable in any real-world deployment. The right behavior is obvious when you say it out loud  an agent should move fast and independently on everything that's clearly within what it was asked to do, and stop the moment it's about to do something that wasn't. vot slow everything down. vot ignore the boundary. snow the difference, in real time, before the action runs. What we want you to solve Build an iI agent that does real autonomous work  automate a workflow, manage a process, handle a domain-specific task, whatever you think is worth building. The agent should use tools (via ukP or otherwise) and naturally encounter a mix of safe routine actions and higher-stakes ones. Then, using the irmorIQ Sls, make the agent genuinely smart about when to proceed and when to stop: it should flow freely through actions that are within its declared intent plan and hold for human approval the moment something falls outside it  not based on vibes or keyword matching, but based on cryptographic verification of whether the action was part of what the agent was originally authorized to do. Every decision, allowed or blocked, should be logged. What good looks like i live demo where you can show the agent completing a real task autonomously, then deliberately trigger an out-of-scope action and watch it get caught and held  before it executes. Then approve it from the dashboard and watch the agent continue. The line between autonomous and gated should be real and verifiable, not hardcoded. You must use irmorIQ Sls  capture_plan(), invoke(), hold/block enforcement. Build the agent and its tooling first, then implement irmorIQ to govern where it runs free and where it stops. Rules for this track ● Your agent must have at least one action it genuinely wants to take, that is genuinely wrong, and that a keyword filter wouldn't catch. If a contains("delete") check would have stopped it, it doesn't count. ● The destructive action must be real. in actual database row, an actual test-mode charge, an actual file. "It would have deleted the table" proves nothing. ● If no ukP server exists for your domain, a mock one is fine. We're judging enforcement, not integration. Problem 2  Who authorized thatg iI agents are getting better at working together. i planning agent breaks down a task, hands pieces off to specialist agents, and those agents go execute  calling iPIs, writing files, sending messages, moving data. It's powerful. It's also completely unaudited. When something goes wrong, nobody can answer the most basic question: who authorized that action, and did the agent that ran it actually have the right tog The moment one agent delegates work to another, trust becomes implicit. The sub-agent inherits whatever context it was given, and there's nothing stopping it from doing far more than it was asked. There's no receipt, no scope boundary, no expiry. The delegation chain is invisible. What we want you to solve Build any multi-agent system that does something genuinely useful  a research pipeline, a customer support system, a code review workflow, a content generation system, anything. The agents should coordinate with each other and use tools (via ukP or direct iPI calls) to get real work done. Then, using the irmorIQ Sls, make every delegation of authority between agents explicit and cryptographically traceable. i sub-agent should only be able to do exactly what the parent authorized it to do  nothing more, nothing less  and every action should leave an auditable trail that shows the full chain of trust from the original user intent down to the final tool call. What good looks like i working multi-agent system where you can point at any tool call and trace it back  which agent ran it, under whose authority, within what scope, and whether it was inside the declared plan. The audit trail should be real, not simulated. You must use irmorIQ Sls  delegate(), capture_plan(), invoke(). Build the agent system first, then wire irmorIQ in to govern it. Rules for this track ● Every sub-agent must have at least one ukP tool of its own. delegate() only takes effect when a sub-agent calls invoke(). i sub-agent that only summarizes or scores never makes a tool call, so its scope restriction is decorative  and we will check. ● Sub-agents must run as separate clients with separate keypairs. nour function calls in one process isn't a delegation chain. ● lemo at least one scope violation, not just the happy path. i pipeline that works is not the same as a pipeline that holds. ● Bonus: show a delegated token expiring, or a sub-agent attempting to re-delegate onward.
